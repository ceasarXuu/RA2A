## 执行记录

### 升级路径（v0.0.12 → v0.0.13 正式 exe）

1. `ra2a stop` graceful 停掉 v0.0.12 daemon（PID 39240），lease 与 managed 一并清理，计划任务被 stop 语义禁用。
2. 下载官方 `ra2a-v0.0.13-windows-amd64.exe`，SHA-256 与 release 附带的 `.sha256` 一致。
3. 旧二进制改名退役（`ra2a.exe.retired-v0.0.12`），发布新二进制到 `~\.local\bin\ra2a.exe`。
4. `ra2a restart` 重新注册并启用计划任务，daemon PID 48304、managed 27360（`.ra2a-48304.sock`）、lease 一致。

### 验证组 2.1 child-only kill（本发布核心路径）

- `Stop-Process` 杀 managed 27360，daemon 48304 不动。
- 5 秒内出现新 managed 49076（同一 `.ra2a-48304.sock`），lease 指向 49076。
- probe 通过：恢复后的 host 返回正常 thread list。

### 额外观察：CLI 与 daemon 的 owner lease 冲突（修复前问题被 supervision 掩盖）

- 执行 `ra2a selftest`（无 `--pin`，用于验证 host 时误用）时，CLI 的 `prepareConfig → cleanupOwnerRecord` 与 daemon 共用同一个 `app-server-control.sock.ra2a-owner.json`，把 daemon 的 managed host 49076 当作陈旧 lease 杀掉。
- daemon 的 `watchProcess` 在约 1 秒后自动拉起新 managed 45168，lease 随之更新 —— **这构成对 supervision 的第二次独立实证**（外部非 RA2A-业务 的进程终止也能被自动恢复）。
- CLI 自身临时 host 的退出事件可观测：`event=managed_codex_host_exited pid=34000 error="exit status 1"`（写入 CLI 进程 stderr，非 daemon）。
- 结论：该冲突在 v0.0.13 下不再造成服务中断（supervision 兜底），但属于既有设计隐患，建议后续让 CLI 只读探测 daemon lease（存活校验）或在 daemon 存活时跳过 cleanup，作为候选改进项。

### 验证组 2.2 stop 无 resurrection

- `ra2a stop` 后 5 秒：managed 进程与 owner lease 均消失，daemon 退出，计划任务禁用。
- 再等 3 秒：无任何 resurrection。

### 验证组 2.3 daemon 强杀 + 计划任务自愈回收

- 前序 runbook `windows-managed-app-server-lifecycle-handoff.md` 无实际 PASS 记录 → 按 runbook 执行。
- `Stop-Process` 强杀 daemon 5452（不杀 managed 41828）。
- 48 秒后计划任务拉起新 daemon 23108（≠ 5452）；旧 managed 41828 已被新 daemon 按 lease 回收（进程不存在）。
- 新 managed 38076（`.ra2a-23108.sock`）与新 lease 一致；probe 通过。

### 验证组 3 真实 LAN（反向 E2E，Mac Desktop 参与）

- Mac（macmini-m4）target 可见且 ready（70 sessions）。
- 杀 Windows managed 38076 → 5 秒内恢复为 46808（单一 writer，`.ra2a-23108.sock`），daemon 23108 不变。
- 恢复后 session discovery 正常：targets 仍为 macmini-m4/rog306 两个规范节点，无 ghost、无重复。
- 双端 Desktop 就绪后，向 Mac "hi" session（01a06efc-b18b-7103-bef6-c3649e33ecee）发送唯一 marker `v0.0.13-group3-marker-20260905003641775`：`POST /v1/send` 返回 200 accepted。
- 用户确认 marker 在 Mac "hi" session 中收到且只出现一次。
- 说明：本组为 runbook 原流程（Mac 端驱动）的 Windows 反向替代（用户确认），投递方向为 Windows → Mac；Mac → Windows 方向的 marker 单次投递依赖同一套 delivery 协议，未单独重跑。

### 验证组 1（Linux native）

- 本机为 Windows，未做 Linux native 执行。
- 代码级前置全过：`git merge-base --is-ancestor` 对 4b7d7d9/0802c30 均 yes；`go test ./...` 全部 ok；`go vet ./...` 无输出。
- 单元测试已覆盖两类 supervision 场景（release notes 所述）；Linux OS 生命周期组留待有 Linux host 的交接方。

## 失败项与限制

- 无失败项。
- 限制：
  1. daemon 侧 `event=managed_codex_host_exited` 在 Windows 计划任务下不可见（runbook 已声明不阻塞验收）。
  2. Group 3 为反向替代，非 runbook 原始 Mac 驱动流向。
  3. `ra2a selftest` 需 `--pin` 且与 daemon 共用 lease（见上文观察），不建议作为 Windows 侧的常规 probe 手段。

- 未用第二个 App Server 代替 Desktop owner 投递。
- 未以版本字符串代替 Git 祖先校验。
